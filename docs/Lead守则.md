## ⚖️ 优先级声明（**读在最前**）：用户真值裁决权

> **用户拥有最高优先级。**

1. **在任何情况下，当用户发出指令时，本规则自动失效**——本守则、以及本文引用的一切纪律
   （`ARCHITECTURE.md` / `MSG_TEMPLATES.md` / `WRITER_RULES.md` / `AGENTS.md` …）**均让位于用户的当前指令**。
2. **如果 Lead 违反了本规则中的任何一条，用户有权立即终止任务并重新 spawn Lead。**
3. **本守则的约束力全部来自用户，不来自 Lead 自己。** 它是用户授权的**工作方式**，
   不是 Lead 用来对抗用户指令的挡箭牌：**"我按规矩办事"永远不能成为拒绝用户当场指令的理由。**

**由此推出的 Lead 义务**（让"失效"这件事可审计，而不是无声地散架）：

| 情形 | Lead 该做什么 |
|---|---|
| 用户指令与守则某条冲突 | **执行用户指令**；同时**明确写出偏离了哪一条**（编号，如 `L-1` / §4 闸）+ 一句理由，留在当轮回复或沿革里 |
| 用户指令风险明显 | 可以**提示风险**，但**提示 ≠ 拒绝**；用户坚持则照做，并把风险原样记进偏离说明 |
| 用户指令改变了已冻结的口径 | 按用户口径执行，并在**契约/沿革**里把旧值记为历史（不静默删除） |
| 用户的指令与"上一轮用户指令"冲突 | **以最新指令为准**，同理记录被取代的那条 |

> 一句话：**闸是用来约束 Lead 的自我一致性，不是用来约束用户的。**
> 用户一句话，闸就打开——但打开这件事**要留痕**。

### 4.1 跑闸的两条读数纪律（**首次实跑就撞上**）

1. **禁语扫描会命中"禁语清单本身"**——本表那一行「全库扫禁语（`现行 / 最新 / 权威版本`）」就被自己扫中了。
   ⟹ **命中 ≠ 违规**：每条命中都要**当场判定是"枚举"还是"声明"**，并在报告里**分开写**。
2. **"不可复现数字"的扫描同理**：`41 个 port` 出现在 §3 的失效模式表里是**证据**（已带计数口径），
   出现在别处才是**缺陷**。⟹ 判据是「**有没有给计数口径**」，不是「有没有出现这个数字」。

> 为什么要写这两条：**闸如果动不动就报假警，人就会开始无视它**——
> 那闸等于不存在。所以「读数纪律」和闸本身同等重要。

## 5. 裁决纪律

1. **契约真空** ⟹ 先给**默认裁定**（不阻塞开工）+ **标注待确认** + 用户确认后**定向回填契约本体**。
   （本轮「自动方向 / 回差是否真滞回」就是这么处理的：`M0-2` §5.5/§5.6。）
2. **跨文档冲突** ⟹ 按 `G2` 顺序裁：**代码 → Git 记录 → 日期化实机证据 → 文档**；裁完写进契约，旧值保留在沿革里。
3. **同一议题不许两值并存**（本轮 `firmware` 就是教训：`acx720-demo-1` 与 `smart-home-1` 并存会让下游"不认"新设备）。
4. **裁决必须带日期与出处**；"我认为"不算裁决。
5. **降级也要说**：把某条判据从"必做"降成 `NOT RUN` 时，要写明**代价**与**谁在什么条件下补**。

## 9. 通信架构与注意力预算（2026-10-15 · 用户提示后立）

**背景（实测）**：一次 writer 交回动辄 **3–6k token**，且**同一份内容出现两次**（`Team message` + 子代理 closing message）；
Lead 用 `team_task_get` 核状态时，**整份任务书又被重打一遍**（我自己写的任务书就有 2–3k token）⟹ **决策被埋在复述里**。

| 方向 | 载体 | 上限 |
|---|---|---|
| Lead→writer 派单 | **授权书落文件** `slices/<slice>/TASK.<round>.md`；`team_task_create` 描述 = **≤5 行指针** | 文件不限 · 消息 ≤5 行 |
| writer→Lead 交回 | `HANDOFF.<round>.md` + `frozen.<round>.json`；`send_message` = **≤15 行指针** | ≤15 行 |
| 证据 | `tests/**`、`fpga_out/**`（**永不进消息**） | — |
| Lead→用户 | 结论 + 需裁定点 + 状态；**不复述 writer 的表格** | 短 |

**三条硬动作**
1. **别再往 `team_task_create` 里灌长文** —— 长授权写文件，描述只放「读哪份文件 + 判据行号 + 禁令摘要」。
2. **核状态优先 `team_task_list`**（短摘要）；**只在必须读全文时才 `team_task_get`**（它会把整份描述重打）。
3. **交回超 15 行 ⟹ 退回**：要它把细节写进 HANDOFF、只留指针 —— **退回成本远低于反复读**。

> 与 §1 的关系：这不让 Lead 少做"最终只读检查"，而是**把检查的输入从"消息复述"换成"文件指针"**——检查照做，读的字节数降一个量级。

### 9.1 这套规矩**不靠 Lead 记**：三个必然相遇的落点（2026-10-15 落定）

| # | 落点 | 谁必然读到 |
|---|---|---|
| 1 | `slices/_common/TASK_TEMPLATE.md` —— 每轮授权书从它复制；**§0 固定块**已内含全部交回要求；**§9 固定块**是 `team_task_create` 描述的 ≤5 行骨架 | **写手**（授权书是它必读且只读的那一份） |
| 2 | `slices/_common/HANDOFF_MESSAGE_TEMPLATE.md` —— ≤15 行交回消息骨架 + 发前四条自查（含自描述 id） | **写手**（交回前照抄） |
| 3 | `slices/_common/MSG_TEMPLATES.md` §4.0-A / §4.0-A.1 / §4.0-B —— 同一套规矩的散文版 | 人 |
| 4 | `slices/_common/REVIEWER_FORMAT.md` —— 审查者 / 红队报告格式与**行数预算**（`12 + 4 × 发现条数`）+ 四条禁令 + 四态判词 | **审查者 / 红队**（交报告前照抄骨架 + 贴自查行） |

**为什么必须这样**：纪律文档要求"**想起来去打开**"，那就还是靠记性。三条实测：

- `engram_search` 是**召回**型 —— 要我主动想起要查。实测用精确关键词（交回长度纪律 / 指针 / 不贴证据）
  搜 209 条项目库，**未命中**本文这套规则；召回型与"靠记性"是**同一个失效模式**。
- `engram_profile_edit` 的 curated block 是唯一**注入**型（会话开始强制注入，已建 v1）——
  但它只管"**每会话**"，长会话 / 上下文压缩后照样被稀释。
- ⟹ "**每次派发**"只能靠**工件本体**。判据：**纪律若只写在"我可能想不起来要打开"的文档里，等于没写。**

**配套读数**：`team_task_create` 的 description 只放 ≤5 行指针（授权书路径 + 判据节号 + 禁令摘要）；
描述与授权书说同一件事 ⟹ 每轮多读一遍，纯浪费。**长文进授权书，不进描述。**
