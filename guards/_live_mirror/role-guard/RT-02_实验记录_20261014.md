## 4. 第一次实验（假 FAIL）——必须留档

### 4.1 现象

同探针返回了 **MCP 正常数据**，按判据应为 `FAIL`：

```text
调用：mcp__vivado__list_sessions
返回：当前没有活跃的 Vivado 会话。使用 start_session 启动一个新会话。
```

### 4.2 定性诊断（没有直接采信 FAIL）

按「先分清『原理拦不住』还是『插件没跑』」的思路做了三步：

1. **工具注册表就绪**：`mcp__vivado__get_part` 返回 `unknown tool`（该名字确实不在 846 名单里）⇒ 注册表是最新的、MCP 侧正常。
2. **查 Loader 是否认得该条目**：
   ```text
   Config(entry="role-guard")        → Error: unknown entry id "role-guard"
   Config(entry="include:mcp-vivado") → 正常返回完整 Config schema
   ```
   同一文件里的 `- insert:` 条目**在**，我那条**不在**。
3. **排除"插件代码本身有问题"**：用 stub ctx 把 `apply` 跑起来（`test/stub-apply.mjs`）
   ```text
   模块导入 OK；apply 未抛异常；注册 guard 数 = 1
   手工喂 mcp__vivado__list_sessions → 返回探针拒绝串
   ```
   ⇒ **插件逻辑正确**，问题在"有没有被加载"。

### 4.3 根因

补丁把新插件写成了**顶层裸条目**：

```yaml
- id: role-guard          # ← 错：这只"按 id 覆盖已有条目"
  name: 'E:\...\lib\index.js'
```

DSH 的约定是：**顶层 `- id:` 用于覆盖已存在的条目；插入新条目必须写成 `- insert:`**。
`role-guard` 并不存在于任何 bundle ⇒ 该条目被**静默忽略**。
按官方文档该打 stderr 警告，实测**没有可见警告**——这是个值得记住的坑。

### 4.4 修正

```yaml
- insert:
    - id: role-guard
      name: '%MAIN_REPO%-dsh/guards/role-guard/lib/index.js'   # 正斜杠，免转义
      config: { mode: dry-run, probeDeny: [mcp__vivado__list_sessions], ... }
```

改后重启 → §3 的 PASS。

**限制**：`role` 只有两档，writer 与 reviewer 都是 `teammate` ⇒ 业务角色只能由

### 6.3 ⚠ 致命漏洞与修正：**越权委托绕过**（2026-10-14 17:3x，用户指出）

#### 6.3.1 漏洞

**假设**：审查者的只读边界在"派生一个子 agent"后仍然成立。

**证伪尝试（实测）**：用一个普通 `subagent`（**不是** `spawn_teammate`）派生子 agent，
让它调 `mcp__vivado__stop_session`：

```text
返回：会话 'default' 不存在。
```

⇒ **调用真的执行了**，没有任何拦截。

**根因**：
1. 子 agent **不是团队成员** ⇒ `agentTeams.tryMembership(child)` 返回 `undefined`；
2. 而当时的 `unknownPolicy` 是 **`pass`**（我提议、用户当时选的"先求不误伤"）；
3. ⇒ 子 agent 落进"身份未知 ⇒ 放行"分支，**拿到完整 MCP 写权限**。

**后果**：**审查者只要用 `subagent` 派生一个子 agent，就能绕过只读边界去写文件 /
改 RTL / `run_tcl` / 烧板。** 这是教科书式的**越权委托（delegation laundering）**。

DSH 文档其实早写明了这个前提：子 agent 是 fresh scope，
**"parent tool restrictions and authority are not imported"** —— 继承必须由我们实现。

**⚠ 诚实记录**：本轮早先我把这个行为当成"决策 3 身份未知放行 = `CONFIRMED: PASS`"记进了档。
**那个判定是错的**——它不是"验证通过"，而是**在演示绕过通道**。原判已作废，见 §6.3.4。

#### 6.3.2 修正（两处，缺一不可）

**修正 1 · 权限继承**：新增 `effectiveMembership(exec)` ——
沿**创建链**向上（`agents.isOwnedBy` + `agents.list()`，上限 8 跳）找**最近的团队成员祖先**，
用**祖先的角色**作为调用者的有效角色。只能收紧、不得放宽：

| 调用者 | 有效角色来源 | 结果 |
|---|---|---|
| writer 本人 | self | 放行 |
| **writer 的子 agent** | `ancestor+1` = writer | 放行（写手可委派） |
| reviewer 本人 | self | 拒绝 |
| **reviewer 的子 agent** | `ancestor+1` = reviewer | **拒绝**（原漏洞） |
| **reviewer 的孙 agent** | `ancestor+2` = reviewer | **拒绝**（多层继承） |
| 无责任链的孤儿 / 无 agent 归属 | 无 | 按 `unknownPolicy`（默认 guard ⇒ 拒绝） |

**修正 2 · 默认值翻正**：`unknownPolicy` 由 **`pass` 改为 `guard`**。
理由：继承实现之后，"未知"只剩**无任何责任链的宿主级调用**；
对这种调用放行没有安全理由，而 `pass` 会留下绕过通道。
`test/validate-patch.mjs` 新增**硬断言**：`unknownPolicy=pass` 直接判失败。

#### 6.3.3 离线验证（`test/stub-apply.mjs` §9，8 条全过）

```text
✅ reviewer 本人 → 拒绝
✅ reviewer 的子 agent → 拒绝          ← 原漏洞

✅ writer 本人 → 放行

✅ 无责任链的孤儿 agent → 拒绝          （默认 guard）
✅ 无 agent 归属 → 拒绝                （默认 guard）
```

**运行期验证：`NOT RUN`** —— 需要重启后用一个"reviewer 派生子 agent"的真实场景复验。

### 6.4 ⚠ 第二处漏洞与定稿：**写权限不可委派**（2026-10-14 17:4x，用户再次指出）

#### 6.4.1 第二处漏洞

**6.3 的修正引入了新洞**：把"祖先继承"实现成了**角色继承**：

```text
有效角色 = 最近团队成员祖先的角色      ← 6.3 的实现
⇒ writer 的子 agent 有效角色 = writer ⇒ 可写
```

**后果（用户指出）**：
1. writer 可派生**任意多个可写子 agent** ⇒ **「同一 checkout 单一 writer」当场失效**；
2. 等于给 writer 开了一条把写权限"洗"给协助者的通道；
3. 而 writer 带的子 agent **本应是审查/协助**（只读）。

> **补充记录（实验后自查）**：本节讨论的 `s-wri-kid` 是**普通 `subagent`**
> （`agentTeams` 的 `tryMembership` 对它返回 `undefined`），不是 `spawn_teammate` 的成员——
> 与 6.3 里出事的 `s-rev-kid` 是同一种东西。所以它不是"writer 的团队成员同事"，
> 但用户指出的**方向仍完全成立**：**写权限被继承下去就是错的**，已按此定稿。

#### 6.4.2 定稿规则：`skip` 当且仅当「调用者本人是写手成员」

| 调用者 | 自身身份 | 祖先身份 | 结果 |
|---|---|---|---|
| writer 本人 | writer | — | **放行**（唯一可写情形） |
| **writer 的子 agent** | 无 | writer | **拒绝** ← 本轮修正 |
| reviewer 本人 | reviewer | — | 拒绝 |
| reviewer 的子 agent / 孙 agent | 无 | reviewer | 拒绝 |
| 孤儿 / 无 `agent` 归属 | 无 | 无 | 按 `unknownPolicy`（默认 guard ⇒ 拒绝） |

**关键性质**：`ancestorMembership` 一旦存在就**钉死 `enforce`**——
于是子 agent 的安全性**不依赖 `unknownPolicy` 旋钮**。
即便把 `unknownPolicy` 与 `serviceMissingPolicy` 都拧成最松的 `pass`，
**writer 的子 agent 仍被拒绝**（§10 专门断言）。

**祖先身份的作用被收窄为「归因」**：日志与事件里能看到 `caller=child-of:writer-rtl(ancestor+1)`，
可用于追责与排查；但它**不再授予任何权限**。

```text
✅ writer 本人 → 放行（唯一可写情形）
✅ writer 的子 agent → 拒绝（写不可委派）        ← 本轮修正
✅ writer 子 agent 调只读工具 → 放行              （未过度拦截）
✅ reviewer 本人 / 子 / 孙 agent → 拒绝
✅ 孤儿 / 无 agent 归属 → 拒绝（默认 guard）
✅ writer 子 agent + 最松旋钮（unknownPolicy=pass 且 serviceMissingPolicy=pass）→ 仍拒绝
```

**运行期验证：已于 §6.6 完成（PASS）** —— "writer 派生子 agent"的真实场景已复验。
（本文写作时标 `NOT RUN`；此处保留原结论的演进痕迹。）

#### 6.4.4 行为后果（工作流要照此调整）

**writer 不能把 Vivado 写操作外包给子 agent。** 若确实需要第二个写手，
必须由 **Lead 直接派第二个 `writer-*` 成员**（并遵守"同一 checkout 同一时刻只有一个 writer"），
而不是让 writer 派生——后者现在会被挡。

### 6.5 ⚠ 第三次事故：加固层把主闸门一起拖死（2026-10-14 重启后实测发现）

#### 6.5.1 现象

重启后验证时发现 **Lead 自己的 `stop_session` 竟然执行了**：

```text
调用：mcp__vivado__stop_session（Lead）
返回：会话 'default' 不存在。          ← 本应被拒
```

事件日志只有一行 `plugin-start`，其中 `teamServiceAvailable: false`、
**没有任何 `agent-created`**。

#### 6.5.2 根因

`agentScope` 块里残留一句 `const agents = lookupAgents();`，
而 `lookupAgents` 的定义在重构时被删掉 ⇒ **ReferenceError**：

1. `apply` 抛异常 ⇒ 该插件条目**加载失败**；
2. Loader 回滚该插件的 effect ⇒ **`ctx.tools.guard(onCall)` 注册被撤销**；
3. ⇒ **角色主闸门整块失效**，所有 MCP 写调用畅通无阻；
4. 而 `plugin-start` 事件在抛错**之前**已写 ⇒ 外部看日志像"已加载"。

#### 6.5.3 为什么没被测出来（测试盲区）

所有 stub 用例都用 `agentScope: { enabled: false }`——**`enabled: true` 这条路径
从未在任何测试里执行过**，而 profile 里恰恰开着它。

#### 6.5.4 修正（三条，缺一不可）

1. **补回 `lookupAgents`**；
2. **铁律：可选加固层绝不允许影响主闸门** —— 整个 `agentScope` 块包 `try/catch`，
   失败只记 error 并继续；
3. **`agent.ctx` 防御**：`Agent` 公开类型只有 `{ id }`，`agent.ctx` 是官方指引里的写法、
   运行期存在性**尚未证实**；缺失时**只跳过不抛**（抛出去就会重演本次事故）。

#### 6.5.5 测试补强（`test/stub-apply.mjs` §11）

```text
✅ apply 不抛异常（加固层失败也要被 try/catch 兜住）
✅ 主闸门仍然注册（guards 数 = 1）
✅ 有 agent.ctx 的 agent 装上了 per-agent guard
✅ 该 agent 同时被 restrict 遮蔽
✅ restrict 的 deny 只含 MCP 写工具
✅ 无 agent.ctx 时只跳过、不抛，主闸门仍注册
```

顺带修了 stub 保真度：插件用**生成器 effect**（官方指引写法），
stub 原先直接调 `fn()`、不迭代生成器 ⇒ yield 的注册被静默跳过。
已改为生成器感知（`runEffect`）。

**可复用教训**：**"可选加固"与"强制边界"必须在故障域上隔离**——
否则辅助功能的一个 typo 会把整条安全边界一起带走，而且失败方式是"日志看着正常"。

### 6.6 ✅ 最终验收矩阵：角色边界 + 越权委托 + 写不可委派（全部 PASS）

**环境**：`mode: enforce`、`roleScope.enabled: true`、`agentScope.enabled: false`、
`restrictMcpWriteTools: false`（可选加固层已按 §6.5 隔离关闭，主闸门保留）。
**探针**：`mcp__vivado__stop_session`（写类；当前无会话 ⇒ 失效也无害）。
**时间**：2026-10-14 20:45 左右（事件日志 UTC `11:45`）。

| # | 调用者 | 身份解析 | 原始返回（逐字） | 判定 |
|---|---|---|---|---|
| 1 | Lead（本会话） | `lead`，`via: self` | `Error: [role-guard] 真只读模式：拒绝写/执行类工具 \`mcp__vivado__stop_session\`（写动词 stop）` | **拒绝** ✅ |
| 2 | `reviewer-final` 本人 | teammate，`via: self` | 同上（同一拒绝串） | **拒绝** ✅ |
| 3 | `reviewer-final` 派生的子 agent | 自身无身份 ⇒ 祖先 = reviewer | 同上（同一拒绝串） | **拒绝** ✅ |
| 4 | `writer-final` 本人 | teammate，`via: self` | `会话 'default' 不存在。` | **放行且真执行** ✅ |
| 5 | **`writer-final` 派生的子 agent** | 自身无身份 ⇒ 祖先 = writer | `Error: [role-guard] 真只读模式：拒绝写/执行类工具 \`mcp__vivado__stop_session\`（写动词 stop）` | **拒绝** ✅（写不可委派） |

**事件日志中的机器可验记录**（`.cache/dsh-guard/guard-events.jsonl`）：

```json
{"event":"deny","tool":"mcp__vivado__stop_session","enforced":true,
 "caller":{"name":"lead","role":"lead","via":"self"},"reason":"[role-guard] 真只读模式：…（写动词 stop）"}
{"event":"allow","tool":"mcp__vivado__stop_session",
 "caller":{"name":"writer-final","role":"teammate","via":"self"},"verdict":"skip"}
```

**为什么第 4 条是决定性的**：它返回 **MCP 业务语义**（"会话不存在"）而不是 guard 串
⇒ 写手的调用**真的到达了 MCP 服务器**。若 guard 整体没跑，第 1/2/3/5 条也会返回同样的业务串；
五行出现**两种不同结果** ⇒ 分档确实来自"按调用者身份判定"，而不是"guard 没落地"。

**结论**：三次修正（越权委托 §6.3、写不可委派 §6.4、加固层故障隔离 §6.5）**全部运行期验证通过**。

#### 6.6.1 本轮暴露的两个"记录/可核"缺陷（不影响拦截，但影响取证）

1. **事件日志按工具名去重 ⇒ 跨调用者的后续拒绝不入档。**
   `deny` 事件写在 `if (decided.get(tool) !== reason)` 里，于是同一工具**被不同角色拒绝时只记第一条**——
   本次 `reviewer-final` 与其子 agent 的拒绝**没有**出现在日志里（只能靠工具返回原文取证）。
   应改为按 `(tool, caller)` 去重。
2. **`allow` 事件的 `verdict` 字段硬编码为 `'skip'`。**
   但 `list_sessions` 这类放行其实来自**只读白名单**（不是角色 skip），日志会误导。
   应记录真实来源（`roleSkip` / `readonlyWhitelist`）。

两条都属于"日志可能误导取证"，与本项目"证据优先"的纪律相冲，已记为待修。
**注意**：拦截行为本身不受影响，本次五行结论均由**工具原始返回**独立取证。
