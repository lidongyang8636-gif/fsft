### ★★ R4.5 更正（红队第 3 轮 D3）—— **"跨任务挪用"没有关闭，而且仍是 `pass`**

上表把 **F2 跨任务挪用**写成"已修"是**过度声明**（把洞说小了），**现更正**：

> **跨任务挪用仍未根除。** R4.3/R4.4 之后它**仍然是 `pass`** —— 前提只有两条：
> **①调用点得出一个有效产物**（存在 ∧ 普通文件 ∧ 非空 ∧ 非链接）
> **＋ ②存在一份新鲜的绿收口证据**；**证据与该产物之间没有任何身份关联**。
> 即：**"绑不上产物"改成了 `ask`，但"绑上了别的任务的产物"依然是 `pass`。**
> R4.2 关掉的是 F2 的**原样复现**（产物 0 个 ⇒ 退化成只看证据自报时间），
> **"跨任务挪用"这个攻击类没有被关闭** —— 它只多了一个"**必须点名一个有效产物**"的前置。

**这条现在是活的最强绕过路径之一**：拿一份**真实有效**的 `.bit`（任何来源）＋ 一份**无关任务**的
新鲜绿收据 ⇒ 放行。**下一轮红队可直接打这条**（本文件§3「跨任务挪用」一节的理论描述**依然成立**）。
**不许**再表述为"只是 `pass` → `ask`"。

### ★ 第 2 轮指出：**R4.2 时"无绑定产物却 `pass`"并没有关闭**

R4.2 的修法只挡住了"**一个候选都没有 / 候选全不存在**"那一类。
**红队第 2 轮 + Lead 第一手复现**证明下面四条在 **R4.2 时仍然 `pass`** ⇒ **R4.3 修**：

| 项 | R4.2 时的行为 | R4.3 |
|---|---|---|
| **M 混合候选**（1 个存在 + 1 个不存在） | **`pass`** —— `missing` 被**完全忽略**，只看 `existing` 的 mtime（**红队与 Lead 各自实机**） | **`ask`** |
| **E 空文件**（0 字节，名为 `*.bit`） | **`pass`**（**Lead 实机**） | **`ask`** |
| **D 目录**（**名字带白名单扩展名**，如 `dir.bit`） | **`pass`**（**Lead 实机**）。⚠ 精度：**无扩展名的目录本来就 `ask`**，**不许**写成"目录一律能过" | **`ask`** |
| **S symlink / junction** | **代码级结论**（`existsSync` 跟随链接）⇒ 预期 `pass`。**双方都无实机**（Lead `symlinkSync` 得 `EPERM`） | **`ask`**；**该分支仍无实机证据，标 `NOT RUN`** |

> **本轮（R4.3）的判据**仍是：**还存在任何"无绑定产物却 `pass`"的路径吗。**
> 新规则：**任一被点名的候选不合格 ⇒ `ask`**（不存在 / 链接 / 目录 / 空文件 / 非普通文件），
> 理由写明**是哪一条不满足**；**仍不做 `deny`**。
>
> **嵌套对象递归是预期支持，不是漏洞**（红队第 2 轮主动澄清）—— 本文**不**把它当攻击面。

## 0 先把它的能力说清楚（免得红队打空气）

它**只能**做一件事：在 `tools/pre-execute` 这个 waterfall 上，对**字面名单内**的 13 个 MCP 工具，
按"有没有新鲜收口证据"给出 `ask` / `deny` / 放行。**名单**（`BURN_TOOLS`）：

```
mcp__vivado__program_device, mcp__vivado__generate_bitstream,
mcp__fpga-mcp__program_device, mcp__fpga-mcp__generate_bitstream,
mcp__fpga-mcp__viv_program_flash, mcp__fpga-mcp__viv_program_hw_device,
mcp__fpga-mcp__viv_erase_flash, mcp__fpga-mcp__viv_write_bitstream,
mcp__fpga-mcp__viv_write_bitstream_with_ltx, mcp__fpga-mcp__viv_xsct_download_bitstream,
mcp__fpga-mcp__q_program_device_pgm,
mcp__fpga-mcp__a_program_device, mcp__fpga-mcp__a_generate_bitstream
```

名单**之外**的一切（包括 `pwsh`、`Bash`、`Read`、所有 `report_*`/`get_*`、以及 `run_tcl`）**一律放行**。

## 1 `run_tcl` 是最大的洞 —— **MCP 通道内的任意执行**（最高优先级）

- **怎么走**：`mcp__vivado__run_tcl` / `mcp__fpga-mcp__exec_tcl`（以及 `safe_tcl`）能执行任意 Vivado Tcl。
  一条 `program_hw_devices` / `write_cfgmem` / `create_hw_cfgmem` + `program_hw_cfgmem` 就完成了烧板与固化，
  **完全不经过**名单里的任何工具名。
- **为什么现在拦不住**：我**有意**没把 `run_tcl` 放进拦截面（TASK.4 §3.1 明令"窄，不许扩成通用审批层"）。
  `run_tcl` 既能读也能写，拦它等于把门扩成通用审批层。
- **红队怎么验**：构造一次 `mcp__vivado__run_tcl` 调用，Tcl 内容为 `program_hw_devices`，确认它**不被拦**。
- **可能的缓解（未做，且需要设计权衡）**：对 `run_tcl` 的**参数文本**做模式匹配（`program_hw_devices|write_cfgmem|…`）
  再分级。**这是模式匹配，会被注释/变量拼接/Tcl 转义绕过**，所以它只能提高成本，不能封死。
  **我倾向不做**，因为"看起来拦住了"比"明确不拦"更危险。

## 2 `pwsh` / `Bash` 里直接起 Vivado —— **完全在 MCP 之外**

- **怎么走**：`pwsh` 里跑 `vivado -mode batch -source burn.tcl`，或直接调 `program_hw_devices` 的等价工具。
- **为什么现在拦不住**：本门只看工具名，`pwsh` 不在名单里；而且**是否允许 shell 起 Vivado 是项目纪律**，
  插件没有能力也没有授权去读命令行文本做判定。
- **红队怎么验**：一次 `pwsh` 调用里写 `vivado -mode batch -source <烧板 tcl>`，确认零拦截。
- **缓解**：**无**。这条要么靠纪律，要么靠更外层的沙箱/审批（不是本插件）。

## 3 跨任务挪用：任何一份"新鲜绿收口"都能授权任何一次烧板

> **状态：★ 仍然成立（R4.2/R4.3/R4.4 均未关闭）。** R4.3 只加了"必须点名一个**有效产物**"的前置，
> **证据与该产物之间仍然没有任何身份关联** ⇒ 这一节描述的攻法**照旧可用**（见上方 ★★ R4.5 更正）。

- **怎么走**：跑一个**无关的**任务（例如改一份文档），让 `gate/close.mjs` 收口产生 `close-*.md`；
  然后烧一块与那份证据**毫无关系**的板子。本门只看"最新一份绿收口是否新鲜"，**不校验任务与产物/板子的绑定**。
- **为什么现在拦不住**：证据里没有"板卡序列号 / 目标器件 / 产物路径"这类字段可供绑定；
  `close.mjs` 的 `pins` 钉的是**判据机器与描述符**，不是"这次烧的是哪块板"。
- **红队怎么验**：造一份与烧板无关的绿证据 + 收口块 ⇒ 观察烧板工具被**放行**。
- **可能的缓解（未做）**：要求证据里出现与本次调用产物路径匹配的 `hashFiles`/`files` 条目。
  代价：现有 5 个域都没有这种条目 ⇒ 会立刻把全部烧板变成 `ask`。需要与 Lead 定口径。
- ★ **D5（红队第 3 轮）：日志/`basis` 里那句「已绑定产物 N 个」表述过强 —— 读的时候不要当真**。
  它**只**证明三件事：① 参数里点名了**有效文件**（存在 ∧ 普通文件 ∧ 非空 ∧ 非链接）
  ② 证据/收口时间**晚于**该文件 mtime ③ `pins` 未漂移。
  它**没有**证明"这份证据是为**这个**产物（或这个任务、这个目标器件）产生的"。
  ⇒ **「已绑定产物」只表示"参数点名了有效产物"，不代表证据与产物之间存在身份关联。**
  （这句字符串在**已冻结的插件代码**里，本轮**不许改**；只能在这里把读法写准。）

## 4 名单是**字面**的：改名/新增的烧板工具直接绕过

- **怎么走**：任何**没被逐字列出**的工具。现实里至少三种：
  ① MCP 服务器升级/改名（`mcp__vivado__program_device_v2`、新服务器 `mcp__jtag__program`）；
  ② 别的后端新增的烧录工具；③ 第三方 MCP 服务器。
- **为什么现在拦不住**：判定就是 `BURN_TOOLS.includes(name)`。
  `WATCH_RE`（program|flash|bitstream|…）**只记日志、永不拦截** —— 它是**观察**，不是第二道防线。
- **红队怎么验**：用一个**不在名单里但语义等价**的名字（如 `mcp__fpga-mcp__viv_program_device`，
  注意名单里是 `program_hw_device`）确认放行，并去日志里找 `"action":"watch"` 行。
- **缓解（部分，已做）**：`watch` 日志让"名单该扩充"这件事**可见**。可见 ≠ 拦住。

## 5 伪造证据：**没有签名**

- **怎么走**：手写一份 `gate-evidence/v0` JSON（`gateOk:true`、`counts.PASS:1`、`finishedAt` 是刚才、
  `pins` 指向真实文件并写对哈希）+ 一个 `close-*.md` ⇒ 本门判 `pass`。
- **为什么现在拦不住**：证据是普通文件、无签名、无 MAC；`close.mjs` 与插件**都**只做"自洽性"检查。
  一致性 canary（插件 vs `close.mjs`）**不防伪造** —— 两边都信任文件。
- **红队怎么验**：按上面手写一份，观察放行。
- **可能的缓解（未做）**：证据里带 HMAC（密钥放在插件外、由 Lead 管）。这需要密钥分发与轮换设计，
  且**仍然**只是把信任从"文件"移到"密钥"；不是本轮范围。

## 6 时间戳是**自报**的 ⇒ "新鲜"可被伪造

- **怎么走**：把一份**旧的**证据 JSON 的 `finishedAt` 改成一个**未来的**时间戳（或把产物的 mtime
  用 `utimesSync` 往回改）⇒ `isFresh` 判真。
- **为什么现在拦不住**：`isFresh` 比的是**文件里写的字符串**与产物 mtime；两者都可被写者操纵。
  插件的"新鲜"**不是**来自可信时钟或不可篡改记录。
- **红队怎么验**：写一份 `finishedAt` 在未来 1 小时、其余自洽的证据 + 收口块 ⇒ 观察放行。
- **缓解（部分）**：`pins` 会抓**内容**漂移。但时间戳**不在** pins 里 ⇒ 单改时间戳不会触发漂移。

## 7 fail-open 是**硬要求**，因此也是**可利用的**

- **怎么走**：让插件在判定前**抛异常**。最省事的几种：
  ① 让 `exec.arguments` 变成一个 getter 就抛（我在 canary 里就是这么测 fail-open 的）；
  ② 让证据目录变成一个**文件**（`existsSync` 真、`readdirSync` 抛）；
  ③ 制造一个超大/不可读的证据文件让 `readFileSync` 抛。
- **为什么现在拦不住**：这是**有意的**设计（TASK.4 §3.3 硬要求）：插件自身异常必须放行，
  绝不许因为插件坏了把所有工具堵死。攻击者拿到的是"把门关掉"的能力。
- **红队怎么验**：注入任一异常 ⇒ 观察**放行**，并确认日志出现 `"action":"fail-open"`。
- **缓解（部分）**：日志留痕（`action:"fail-open"`）。**日志不拦人。**

## 8 逃生舱 = 单点开关

- **怎么走**：`GATEGUARD_OFF=1`（或任何非空非 `0`/`false` 的值）⇒ 整层关闭，
  **连"无证据 ⇒ ask"都不做**，直接放行（仍走 `next()`）。
- **为什么现在拦不住**：这是 TASK.4 §3.4 要求的逃生舱。
- **红队怎么验**：设环境变量 ⇒ 观察烧板工具被放行 + 日志 `"action":"off"`。
- **注意**：插件读的是 `config.env || process.env` ⇒ **谁能改宿主进程环境，谁就能关掉这道门**。

## 9 TOCTOU：判定与执行之间的窗口

- **怎么走**：`classifyBurnCall` 读完证据/哈希之后、宿主真正派发工具之前，替换被烧的 `.bit`
  或改回被漂移检测抓到的文件。
- **为什么现在拦不住**：判定是**时点快照**，执行是之后的事；两者之间没有锁、没有第二次校验。
- **红队怎么验**：让证据通过判定，然后在**同一 tick 内**替换产物再触发工具（需要并发/钩子，较难，但窗口真实存在）。
- **缓解**：**无**。（同族风险 R1.1 已记过：`noWrite` 也检测不到"改完又改回去"。）

## 10 我**故意**排除的"前置/准备类"工具（边界声明，不是漏洞但可被利用）

以下四条**不在**拦截面，理由是"它们不改变硬件、只配置本次会话"，但它们能**改变后续烧板的内容/目标**：

```
mcp__fpga-mcp__viv_set_hw_device_program_file   # 指定接下来要烧哪个位流
mcp__fpga-mcp__viv_add_flash_config             # 配置 flash 器件
mcp__fpga-mcp__viv_set_flash_property           # 设置烧写属性（含地址范围）
mcp__fpga-mcp__q_load_package_programmer        # 装载 programmer 包
```

- **怎么利用**：先用它们把"要烧的东西"改成任意文件，再走**允许**的烧板路径（或配合 §1/§2）。
- **红队怎么验**：确认这四条零拦截（我在 canary A4 里也断言了它们零拦截 —— 那是**有意的边界**，
  红队要打的是"这个边界是否可接受"，而不是"它坏了"）。

## 11 `ask` 在无 UI / 无 agent 的上下文里**退化成 `deny`**（行为与直觉不符）

- **实测依据**（`PRESECUTE-PROBE.md` §2.2，读宿主实现）：
  `serviceAsk` 在 ① `approval` 服务不存在、或 ② `exec.agent === undefined` 时，**直接返回 `deny`**。
- **后果**：在 agent-less 的执行环境里，"无证据 ⇒ ask"实际是"无证据 ⇒ **拒绝**"。
  这**更严**（不是绕过路径），但它意味着**"ask 会问一下"这个描述在那些上下文里是错的**；
  也让"本门会不会误伤"的答案变成情境依赖。
- **红队怎么验**：激活后，在无 agent 的上下文里触发一次烧板工具，观察它是"卡住等人点"
  还是"直接错误返回"。
- **NOT RUN**：本轮**未激活**，所以这条是**读实现**得到的推断，**没有实机观察**。

## 12 我认为最该先打的三条（给红队排优先级）

1. **§1 `run_tcl`** —— 它让"名单"在 MCP 通道内基本失去意义；判据最简单（一条 Tcl 就能上板）。
2. **§5/§6 伪造与时间戳** —— 它检验"证据可信度"这条链到底有多软；
   若能被伪造，那么前面所有分级都只是**对诚实者的约束**。
3. **§3 跨任务挪用** —— 它检验"新鲜绿收口"这个判据**是否真的与上板对象绑定**；
   我承认现在**没有绑定**。

## 13 我不打算掩饰的事

- 本门**拦不住**一个**有意**绕过的人。它拦的是"顺手就烧了"和"忘了先收口"。
- 上面 11 条里有 **6 条我没有缓解措施**（§1 倾向不做、§2、§4、§6、§8、§9）。
- 一致性 canary 只保证"**两份实现不漂移**"，**不保证**"判定是对的"。
